# 查询理解与术语系统重构要求

## 1. 背景

当前项目已经将中文查询词、意图规则、索引文本和提示词集中到
`src/locale/`，但集中管理并不代表现有内容已经具备足够的准确性和
可维护性。现状仍包括以下问题：

- Schema 自动扩展可能从一个词产生数百个候选词。例如当前数据中，
  “保存”可扩展出约 220 个词，“加载”约 259 个，“移动”约 367 个。
- 同义词采用无方向的整组并集，容易让“保存”“加载”“文件”等概念
  相互串联。实际查询 `Array 保存` 会返回 `Load` 和 `Set from JSON`。
- 翻译规则边界过宽，例如 `中文教程怎么做` 会被误判为术语翻译。
- 手工扩展表包含大量通用词。同一个“动作”出现在多个扩展入口中，
  容易降低检索精度。
- `scripting` 关键词已经定义，但未进入当前 ACE 分类路径。
- LLM 扩展对一组输入只生成一份结果，然后把相同结果合并给每个输入
  词，无法保留扩展词与原始词之间的归属关系。
- LLM 提示词目前缺少 Construct 3 领域约束、候选插件限制和严格的输出
  校验规则。
- `QueryExpander` 和 Semantic Chain 尚未进入默认 API 运行路径，因此单独
  调整提示词不会改善默认查询效果。

本次重构不能默认现有查询架构和功能划分是正确的。应先回到产品目标，
重新证明每项能力是否必要，再决定保留、简化、重写、删除或继续调研。
只有确认必要的能力，才进入关键词精度和提示词优化。

## 2. 产品方向复核

### 2.1 当前产品基线

根据当前项目说明，本项目首先是面向 Construct 3 问答的结构化参考数据，
仓库内数据可以被 LLM、脚本和其他工具直接读取；关键词查询和语义检索 API
属于可选服务。因此不能把“建设更复杂的查询智能层”自动视为产品目标。

产品方向复核必须先回答以下问题：

1. 核心用户是谁：直接读取数据的 LLM、调用 API 的应用，还是人工搜索用户？
2. 用户最重要的任务是什么：准确找到 ACE、理解手册、查找示例、翻译术语，
   还是生成完整解决方案？
3. 哪些能力是核心交付，哪些只是可选增强或实验能力？
4. 默认离线、低部署成本和数据可审计性是否比更复杂的语义推理更重要？
5. API 应提供精确资料检索，还是承担通用问答代理的查询规划职责？

在这些问题得到明确答案前，不得以现有模块、测试数量或历史投入作为继续
保留某项功能的理由。

### 2.2 错误方向污染审计

必须假设历史实现中可能存在以下情况：

- 最初问题定义错误，后续模块只是围绕错误假设不断补丁。
- 为修复低质量扩展而增加更多词表、分类层和提示词，进一步放大复杂度。
- 测试只验证当前实现，没有验证真实产品结果，因而把错误行为固化成兼容要求。
- 文档和注释根据实现反推设计理由，使历史偶然选择看起来像既定架构。
- 已不在运行路径中的实验代码仍影响配置、依赖、模块边界和后续决策。

审计时应为每项相关能力建立记录，至少包含：

| 字段 | 要求 |
|---|---|
| 用户问题 | 它解决哪个真实用户任务 |
| 当前调用路径 | 默认 API、可选模式、测试专用或完全未调用 |
| 最初假设 | 当初为什么引入，证据是否仍成立 |
| 当前证据 | 真实查询、日志、用户反馈或基准数据 |
| 维护成本 | 代码、依赖、部署、数据更新和认知成本 |
| 替代方案 | 更简单的规则、直接数据访问、统一检索或删除 |
| 产品决定 | 保留、简化、重写、删除或继续调研 |
| 退出条件 | 用什么指标证明决定正确 |

现有单元测试只能证明代码符合当前实现，不能单独证明功能具有产品价值。
如果测试保护的是已确认的错误行为，应先改写产品预期，再修改或删除测试。

### 2.3 必须重新评估的能力

以下能力不得默认保留：

| 能力 | 必须回答的问题 |
|---|---|
| Direct Lookup | 是否确实提高准确率，错误截获 RAG 的代价有多大 |
| 独立术语翻译意图 | 是否需要独立路由，还是直接查询双语 Schema 即可 |
| 手工同义词表 | 是否优于受控 Schema 检索，维护成本是否可接受 |
| Schema 共现扩展 | 共现是否代表用户语义，是否应该被 IDF/字段权重替代 |
| Tier 2 意图模板向量 | 是否比规则加统一检索有稳定增益 |
| Tier 3 Ollama 分类 | 可选本地模型是否值得部署、延迟和维护成本 |
| QueryExpander | 是生产所需能力、实验模块，还是未完成的历史残留 |
| Semantic Chain/HyDE | 是否解决已证实问题，还是通用 RAG 模式的过度引入 |
| 多集合 Qdrant 路由 | 当前集合拆分是否提高检索质量，还是增加路由复杂度 |
| Reranker 与多路融合 | 在 Construct 3 数据规模上是否有可测量收益 |
| 示例项目索引 | 用户是否需要独立示例检索，标签质量是否足够 |

每项能力至少要与一个更简单的基线比较。没有显著质量收益，或者收益不足以
抵消部署和维护成本时，应优先简化或删除，而不是继续增加补丁。

### 2.4 产品研究要求

进入架构决定前，应完成以下调研：

- 从 README、现有 API、真实问题记录和用户使用方式整理主要任务清单。
- 检查 Construct 3 官方数据实际能直接回答哪些问题，避免重复建设推理层。
- 对精确字段查询、关键词检索、稀疏检索、向量检索和混合检索建立可比较基线。
- 检查当前集合划分、字段权重和双语数据质量，而不是先假定查询词需要扩展。
- 对需要外部模型的方案评估准确率、延迟、内存、安装成本、隐私和离线能力。
- 需要引用外部技术结论时，优先使用官方文档、原始论文和可复现实验。
- 将调研结论写成决策记录，注明采用方案、拒绝方案、证据和重新评估条件。

调研的结论可以是继续优化，也可以是删除整个模块或合并运行路径。

### 2.5 产品指标与去留门槛

产品评估至少应关注：

- 用户问题是否得到可用且可引用的 Construct 3 资料。
- 错误直接查询率，即本应进入语义检索却被规则提前截获的比例。
- 正确插件、行为和 ACE 的 Top-N 命中率。
- 无结果率和错误高置信度结果率。
- 默认路径的首次响应时间和稳定响应时间。
- 安装步骤、模型大小、外部服务数量和离线可用性。
- 新 Construct 版本发布后的数据与规则维护成本。

一项复杂能力只有在金标集或真实使用数据上取得可重复、具有实际意义的增益，
才能进入默认路径。实验结果相当时，应选择更简单、可解释、依赖更少的方案。

## 3. 核心目标

1. 提高直接查询的准确率，减少关键词扩展产生的错误结果。
2. 让关键词、同义词、语法规则和提示词具有明确边界与维护依据。
3. 默认运行路径保持离线、确定性，并且不依赖外部模型或网络服务。
4. 保持现有 API 请求、响应结构和查询类型名称兼容。
5. 通过可重复的金标查询集衡量修改效果，而不是依靠个别示例判断。
6. 识别并移除由错误产品假设产生的代码、测试、配置和文档。
7. 任何新增复杂度都必须对应明确用户价值和可测量质量增益。

## 4. 变更范围

### 4.1 查询金标测试集

新增不少于 60 条真实查询，至少覆盖：

- ACE 列表、ACE 详情、属性列表和术语翻译。
- 插件、行为以及中英文混合名称。
- 教程、比较、概念、原理等应回退 RAG 的查询。
- “保存、加载、显示、移动、获取、查找、请求”等易歧义词。
- 插件名称与普通英文单词相同或相近的情况。
- 正常查询、缺少插件、未知插件、长句和口语化表达。

每条金标数据必须记录：

- 原始查询。
- 预期意图。
- 预期插件或行为。
- 预期 ACE 类型。
- 必须出现的结果。
- 禁止出现的结果。
- 应直接查询还是回退 RAG。

必须包含以下回归案例：

| 查询 | 预期行为 |
|---|---|
| `中文教程怎么做` | 不得识别为术语翻译，应回退 RAG |
| `Array 保存` | 不得把 `Load` 作为主要结果 |
| `怎么在数组中查找特定数字` | 应命中 `IndexOf` |
| `Sprite 有哪些 action` | 保持现有 ACE 列表行为 |
| `如何实现存档系统` | 应回退 RAG |

测试必须以结构化 fixture 保存，不能只散落在测试函数中。

### 4.2 关键词资源拆分

删除职责过多的 `src/locale/keywords.py`，并将所有语言数据集中到单一
`src/locale/catalog.json`：

- 每个概念和规则使用稳定 ID，只定义一次。
- 可翻译值在同一节点下并排保存 `en-US` 与 `zh-CN`。
- 插件范围、权重、ACE 类型等语言无关元数据不得在各语言间复制。
- 查询正则使用从 ACE 类型别名生成的 `{ace_type}` 占位符，避免重复枚举。
- `resources.py` 只负责读取、结构校验、合并和类型转换，不保存具体语言文案。
- 每个可维护资源必须在值旁声明 `purpose`、`source`、`consumers` 和 `tests`；
  禁止加入无法解释来源、生产用途或回归覆盖的裸 key。
- `gold:*` 来源必须对应 `tests/fixtures/query_gold.jsonl` 中真实存在的案例 ID；
  Schema、运行兼容和人工维护来源分别使用 `schema:*`、`contract:*`、`curated:*`。

意图词、列表/详情/翻译/教程语法、定向扩展和索引提示使用同一个目录结构，
不再散落在 Python 常量或需要跨文件同步的镜像 JSON 中。

每项词表必须注明：

- 使用它的运行路径。
- 适用范围和不适用范围。
- 数据来源或增加原因。
- 对应的回归测试。

已经定义但未接通的 `scripting` 分类必须删除，或者明确接入 RAG 路由。
如果继续保留“出现频率大于某阈值”等数据驱动说明，必须同时提供可重复
执行的生成或统计脚本；否则删除无法验证的统计描述。

### 4.3 同义词扩展模型

禁止继续使用无方向、无范围的同义词整组并集。新的扩展规则至少支持：

- 原始词和目标词。
- 单向或双向关系。
- 适用插件或行为范围。
- 适用 ACE 类型。
- 相关性权重。
- 是否允许继续扩展。

默认只允许单跳扩展，不得因新加入的词再次命中其他扩展组而形成级联扩散。
每个原始词最多加入 12 个扩展词；超过限制时必须按领域相关性和权重截断。

“保存”和“加载”、“显示”和“隐藏”等概念可以有关联，但不得被当成无差别
同义词。反义、上下游操作和同一业务领域必须使用不同的关系类型。

### 4.4 Schema 自动扩展

- 不得把匹配 Schema 节点中的全部共现词直接加入查询。
- 使用节点覆盖率、逆文档频率或等价指标排除高频泛化词。
- 单个原始词最多返回 8 至 15 个 Schema 扩展词，具体值应可配置。
- “保存、加载、移动”等输入不得再生成数百个候选词。
- 扩展结果必须保持确定顺序，不能依赖 `set` 的遍历顺序。
- 自动扩展必须保留来源、得分和命中节点数量，便于诊断。
- 语言停用词和高频领域词应分别管理，不能混为同一份手工黑名单。

### 4.5 意图识别规则

- 翻译规则必须要求明确的翻译句式，不能仅因出现“中文”或“英文”就命中。
- 教程、比较、概念、原理类查询的拦截优先级必须高于翻译和列表匹配。
- 正则表达式应使用明确边界和锚点，避免贪婪捕获整句。
- 规则冲突时应记录最终命中规则和被排除规则，便于调试。
- ACE 类型存在重叠关键词时，必须使用权重或上下文判定，不得仅根据集合相交
  无差别返回多个 ACE 类型。
- 未知插件或模型生成的插件名称必须经过本地 Schema 名称解析验证。

## 5. 提示词要求

### 5.1 关键词扩展提示词

关键词扩展应返回可校验 JSON，并按输入词分别组织结果。例如：

```json
{
  "items": [
    {
      "source": "保存",
      "zh": ["存档", "持久化"],
      "en": ["save", "storage"],
      "scope": ["storage"]
    }
  ]
}
```

提示词必须明确要求：

- 只生成 Construct 3 相关术语。
- 保留插件名、行为名、ACE ID、`3D`、`JSON` 等技术词。
- 禁止输出解释、编号、Markdown 或 JSON 之外的文本。
- 禁止产生输入和候选上下文中不存在的插件名称。
- 每个原始词的返回数量必须受 `top_k` 限制。
- 输出应优先包含可用于中英文 Schema 检索的术语，而不是泛化语义联想。

解析端必须验证 JSON 结构、字段类型、数量上限和词长。校验失败、超时或外部
服务不可用时，应安全回退为空结果，不得影响默认查询路径。

### 5.2 意图分类提示词

- 查询类型和 ACE 类型只能返回预定义枚举。
- 应将本地名称解析得到的候选插件或行为传给模型，禁止自由编造名称。
- 提示词应包含直接查询、教程回退、翻译误判等正例和反例。
- 返回结果必须包含置信度和机器可读的判定代码，不返回自然语言解释。
- 代码端必须再次验证查询类型、插件、ACE 类型和置信度范围。
- 模型结果不得覆盖高置信度规则命中；只能补充规则无法判断的查询。

### 5.3 Semantic Chain

Semantic Chain 当前尚未接入默认 API。本轮不得仅为保留功能而继续增加提示词
或配置。必须先作出以下明确选择之一：

1. 正式接入，并增加端到端测试、配置说明和故障回退；或者
2. 标记为实验模块，隔离其依赖；或者
3. 删除无实际调用计划的实现。

在作出选择前，Semantic Chain 提示词优化不属于高优先级交付内容。

## 6. 运行与兼容要求

- 默认路径只使用规则、受控词表和已提交的 Schema 数据。
- LLM 扩展继续默认关闭。
- LLM 结果只能作为低权重补充，不能覆盖确定性规则结果。
- 默认运行不得访问 LLM、CDN 或其他外部服务。
- 不得在模块导入阶段下载模型、建立网络连接或构建不必要的大型索引。
- 实验性 LLM 路径必须有独立配置、清晰日志和健康状态。
- 对外承诺的稳定 API 字段和结构化匹配结果应保持兼容。内部模块、实验配置和
  未正式承诺的查询层级不得仅以“历史兼容”为由保留。
- 所有查询语言资源继续集中在 `src/locale/catalog.json`；算法和
  传输层不得重新嵌入任何具体语言的词表或文案。

## 7. 测试与验收标准

完成条件如下：

1. 原有测试全部通过。
2. 新增金标查询测试全部通过。
3. 每个原始词的手工扩展和 Schema 扩展均不超过配置上限。
4. 相同输入在相同数据版本下多次运行，意图、扩展词顺序和结果顺序一致。
5. 默认 API 测试期间不访问 LLM、CDN 或其他外部服务。
6. `Array 保存` 等已知污染案例不再返回被禁止的高排名结果。
7. 翻译、教程、比较和列表规则不再发生已记录的优先级冲突。
8. 所有模型输出均经过结构和枚举校验，异常时能够安全回退。
9. 生产代码中的中文查询资源集中度检查通过。
10. API 兼容测试通过。
11. `python -m pytest -q`、Python 编译检查和 `git diff --check` 通过。
12. 完成产品能力审计表，并为每项复杂查询能力给出有证据的去留决定。
13. 至少完成一个“不使用查询扩展”的简单基线，与当前方案进行同集对比。
14. 已确认无产品价值或无运行调用的代码、配置、依赖、测试和文档已一并清理。

除通过率外，应输出至少以下质量统计：

- 意图分类准确率。
- 错误直接查询率，即本应回退 RAG 却被规则截获的比例。
- 插件或行为解析准确率。
- Top-N 必须结果命中率。
- 禁止结果出现率。
- 单词平均扩展数和最大扩展数。

## 8. 文档与注释要求

- 更新架构文档中的查询路径和模块边界。
- 更新配置说明，明确确定性路径与实验性 LLM 路径。
- 在 `docs/decisions/refactoring-audit.md` 记录本轮完成项和保留项。
- 注释应解释规则存在的原因、边界和测试依据，而不是复述代码。
- 不在 README 中维护容易失效的词表数量或测试数量。
- 词表调整必须在变更说明中列出新增、删除和行为变化。
- 新增产品能力决策记录，避免以后根据遗留实现重新推导产品方向。
- 对删除的历史能力记录删除原因和恢复条件，不保留失效代码作为“备用方案”。

## 9. 建议实施顺序

### 第零阶段：产品方向与历史假设复核

1. 明确核心用户、主要任务、默认产品形态和可选能力边界。
2. 绘制真实运行调用图，标出默认、可选、实验和未调用模块。
3. 建立能力审计表，对每项能力给出保留、简化、重写、删除或调研决定。
4. 建立无查询扩展的简单检索基线。
5. 审查现有测试、注释和文档是否固化了错误假设。
6. 形成产品与技术决策记录后，再批准后续实现范围。

### 第一阶段：基线与规则修正

1. 建立金标查询集和质量统计工具。
2. 修复翻译、教程、列表等规则冲突。
3. 增加已知误判和污染案例的回归测试。

### 第二阶段：确定性扩展重构

1. 拆分关键词资源模块。
2. 将同义词集合替换为有方向、有权重和有范围的扩展规则。
3. 限制 Schema 自动扩展数量并引入频率权重。
4. 输出稳定的扩展诊断信息。

### 第三阶段：可选 LLM 路径

1. 明确 `QueryExpander` 和 Semantic Chain 的保留或接入策略。
2. 将提示词改为 Construct 3 专用结构化输出。
3. 增加输出校验、超时、回退和端到端测试。
4. 只有达到金标集质量要求后，才允许通过显式配置启用。

## 10. 提交要求

建议至少拆分为三个可独立审查的提交：

1. 产品方向审计、调用图、决策记录、简单基线和金标测试。
2. 经审计确认需要保留的确定性关键词、语法规则和 Schema 检索调整。
3. 经实验证明确有价值的可选 LLM 提示词、结构化输出和实验配置。

不得把 Schema 数据更新、无关格式化或其他功能修改混入上述提交。
