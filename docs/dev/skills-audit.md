### S01：中断恢复把备份当作可丢弃的残留

位置：[export_project.py](../../skills/construct3-agent-plugin/scripts/export_project.py)，第 588–626、636 行。

替换顺序是先把 `web` 改名为 `web.old`，再把 `web.new` 改名为 `web`。进程在两次改名之间被终止时，`.old` 是唯一的旧导出；`run()` 开头及 `unpack()` 开头的 `clear_beside()` 却会无条件删除持有 `data.json` 的 `.old` 和 `.new`。

探针构造这个中断后的磁盘状态：`web` 不存在，`web.old` 保存旧导出及哨兵文件。重试传入版本不符的新包，脚本拒绝新包，但旧备份已被清理，两个目录都不存在。没有实际终止浏览器进程；复现的是替换步骤之间可到达的恢复状态。

建议：在清理之前恢复或明确保留唯一备份；用操作状态区分“替换已完成、可清理的备份”和“替换未完成、必须恢复的备份”。恢复不能依赖下一次导出成功。

验收：在每个改名步骤之后模拟中断，再分别执行成功和失败重试；至少保留一份可用旧导出。替换及恢复都失败时，报告实际备份路径，不能声称原路径保持原样。

### S02：文件名不足以证明目录属于导出器

位置：[export_project.py](../../skills/construct3-agent-plugin/scripts/export_project.py)，第 565–597 行。

`refused_folder()` 对非空目标只检查是否存在 `data.json`，没有验证内容或由谁创建。`clear_beside()` 对固定同级目录更宽松：只要有该文件就递归删除，连目标校验中对 `project.c3proj` 的拒绝也没有。

两个反例均复现：一个保存测量数据和笔记的目录通过目标校验，成功导出后笔记消失；一个既有 `data.json` 又有 `project.c3proj` 的 `web.new` 目录，被清理函数完整删除。主目标是缺失目录时，同级目录也照样被清理。

影响不只来自填错 `--to`。固定 `.new`、`.old` 名称碰到用户已有目录，也会让一次正常导出删除未授权的内容。仅增加 Web 格式特征仍不能证明固定同级目录属于这次操作。

建议：临时目录使用唯一名称和可核验的操作标记；未知同级目录停止并报告。已有导出采用明确的管理标记或一次性接管流程，并保护导出目录中后来加入的用户文件。

验收：普通数据目录、含 `data.json` 的项目目录、无关 Web 产物及同名邻居都保持原样；导出器自己的目标和临时目录可正常替换及恢复。

### S03：回滚没有区分本次写入和其他进程的保存

位置：[edit_sheet.py](../../skills/construct3-agent-plugin/scripts/edit_sheet.py)，第 754–769、900–927 行。

`--new` 只检查目标事件表是否出现；清单仍使用启动时的 `project.data`。回滚快照在验证结束后才读取，写入前没有核对清单版本。失败后，`put_back()` 又把快照里的所有清单和布局恢复，只要字节不同就覆盖，不检查该文件是否被本次调用写过。

正常路径探针在最后一次验证后模拟另一个进程保存清单说明。命令返回 0，但说明被旧的 `project.data` 覆盖。失败路径探针在清单写入失败时模拟另一个进程更改布局名；本次调用尚未写任何布局，回滚仍覆盖那个布局，随后输出“nothing was written”。两种情况都丢失了并发保存。

建议：为整个写入集保存读取版本，提交前核对；冲突时停止，让调用者重新读取。只回滚本次成功写入且仍等于本次写入内容的文件；遇到其他版本时保留并报告，或使用跨进程锁协调完整事务。

验收：在验证后、每个写入步骤间及回滚前插入并发保存，其他进程的修改始终保留；冲突和部分恢复的报告与磁盘实际状态一致。

### S04：倒计时判定仍接受过早重启和无法解释的条件

位置：[grade.py](../../skills/construct3-agent-plugin/evals/grade.py)，第 129–167 行；[test_skill_grade.py](../../tests/test_skill_grade.py)，第 89 行起。

`runs_out()` 只计算条件在 30、0、−0.5 的真假。`倒计时 <= 29` 在这些点上满足要求，但从 30 每帧扣除 `dt` 后，约 1 秒就会重启。另一个漏洞是无法解析的比较返回 `None`，调用者用 `is not False` 接受它；`倒计时 > (1 - 1)` 等价于已被拒绝的 `倒计时 > 0`，却继续通过。

探针分别构造以上两个完整项目：checker 没有错误或警告，评分器的全部断言通过。正确的 `倒计时 <= 0` 对照也通过。这里只运行离线 checker 和评分器；没有把它们当作真实编辑器运行验证。

建议：任务验收描述持续时间和重启时刻，不能仅判断两个端点。离线判定无法解释的表达式标为未验证；行为通过需要观察到中间时刻不重启、到期后重启、第二轮重新计时。

验收：拒绝阈值 29、10 以及等价的反向条件；覆盖禁用事件、额外守卫、Timer 和 `dt` 两类实现。正确实现应在合理帧误差内完成完整两轮。

### S05：checker 的使用错误也被当作正常检查结果

位置：[trace.py](../../skills/construct3-agent-plugin/evals/trace.py)，第 68–79 行。

`lost_calls` 的豁免条件是 shell 命令包含 `check_project.py`，没有识别返回的是项目 findings、参数错误还是脚本异常。

探针实际执行一个未知参数，命令失败并返回 usage 错误；把这个结果写成工具 transcript 后，`by_tool.failed` 是 1，`lost_calls` 却是 0。它会低估错误调用成本，也会掩盖技能文档和脚本参数不一致造成的损耗。

建议：只豁免成功完成检查后报告的项目 findings。增加结构化结果，或核对明确的 findings 输出；不能用命令名豁免整个 shell 调用。测试覆盖参数错误、Traceback 和一条命令中其他失败的子命令。

### S06：客户端包装进程使超时失去上限

位置：[run_trigger_eval.py](../../skills/construct3-agent-plugin/evals/run_trigger_eval.py)，第 84–105、111 行。

定时器只调用 `proc.kill()`，读取循环仍阻塞等待 stdout。若 `--client` 是一个启动子进程的包装命令，子进程继承 stdout 后，父进程被终止并不会关闭管道，也不会停止子进程。

模拟客户端先发送合法 assistant 消息，启动持有 stdout 4 秒的子进程，再等待。配置 1 秒超时，`run_once()` 约 4 秒后才返回 `timed out`。这验证了超时不能限制等待时间；长期运行的真实模型子进程没有执行。

建议：管理整棵进程树，在超时或触发完成后统一停止；stdout 读取也要有独立截止时间。用能继承管道的包装客户端测试，而不只测单进程 `sleep`。

验收：包装命令及其子进程在超时后都停止，调用在允许的清理余量内返回；没有遗留写入临时项目的进程。

### S07：导出数据解析失败没有进入清理和报告路径

位置：[export_project.py](../../skills/construct3-agent-plugin/scripts/export_project.py)，第 503–509、603–624 行。

`exported_versions()` 直接读取 JSON 的 `project` 键。`unpack()` 的异常处理只覆盖 `Stop`、`OSError` 和 `BadZipFile`，不覆盖 JSON 解析、键缺失及字段类型错误。

探针传入持有合法 `data.json` 文件名、但缺少 `project` 的 ZIP：抛出 `KeyError`，留下 `web.new`。旧输出确实保留，因此这一项不算旧文件损失；问题是统一失败说明和清理承诺没有覆盖内容校验失败。

建议：解析时校验 JSON 与字段类型，把可预期的格式错误转为 `Stop`，在统一清理路径退出。不要用捕获所有异常掩盖程序错误。

验收：缺键、不合法 JSON、错误字段类型及无法解码的内容都保留旧输出、清理本次临时目录，并返回可操作的格式错误说明。
