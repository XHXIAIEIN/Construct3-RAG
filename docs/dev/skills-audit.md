## 已验证的问题

### R01：导出输出路径可能指向项目本身或其父目录

位置：[export_project.py](../../skills/construct3-agent-plugin/scripts/export_project.py)，第 561–566、645 行。

`--to` 经过 `resolve()` 后直接交给 `unpack()`，后者执行 `shutil.rmtree(folder)`。没有拒绝项目根目录、项目的父目录、文件系统根目录，或包含其他项目的目录。

安全探针在临时项目中执行 `--to . --dry-run`，命令返回 0，并把项目根目录列为导出目标。随后对同一临时目录调用实际解包函数，`project.c3proj` 被删除，目录中留下导出包的 `data.json`。这验证了路径解析和删除行为；没有登录账号执行完整导出。

影响：一次输出路径误填，就可能删除工程和其 Git 历史。`--to ..` 等祖先目录也缺少保护，但探针只删除了自己创建的临时项目。

建议：在浏览器启动前校验最终路径；拒绝项目根、祖先目录和磁盘根。已有非导出目录应通过可识别的导出标记保护。指定外部导出目录仍可支持，但不能把任意已有目录当作可清空产物。

验收：上述危险路径全部在写入前被拒绝，目标目录保持原样；正常 `.build/web` 导出可用。

### R02：解压或版本验证失败发生在旧导出被删除之后

位置：[export_project.py](../../skills/construct3-agent-plugin/scripts/export_project.py)，第 561–566、607–614 行。

脚本先清空输出目录，再解压，最后检查导出版本。一个 ZIP 中存在 `data.json`，并不足以证明其内容、CRC、版本和完整性都可用。磁盘错误、解压失败或版本不符，都可能发生在上一份导出已被删除之后。

探针创建一份带 `usable.html` 的旧导出，模拟 `extractall()` 抛出 `OSError`。异常发生后，`usable.html` 已不存在。这里只模拟了 I/O 失败；版本不符导致同样先覆盖后拒绝，可从调用顺序确认。

建议：解压到同级临时目录，完成内容和版本校验后替换目标；替换失败时保留旧目录。不要用 `ignore_errors=True` 隐藏旧目录清理失败。

验收：解压异常、版本不符和替换失败时，上一份可用导出的文件与哈希都保持原样。

### R03：`edit_sheet.py --new` 只能保证单文件替换，不能保证整个项目一起写成

位置：[edit_sheet.py](../../skills/construct3-agent-plugin/scripts/edit_sheet.py)，第 882–896 行；[SKILL.md](../../skills/construct3-agent-plugin/SKILL.md)，第 234–247 行。

新增事件表依次写入事件表文件、`project.c3proj` 和需要关联的布局。单个文件使用 `os.replace()`，但任一步失败都没有回滚前面已经写入的文件，也没有统一保护所有文件的读取版本。

探针对 `project.c3proj` 的写入注入失败后，新事件表仍然存在，清单保持原样。再次执行同一计划被拒绝，提示文件存在但未被清单列出。一个通过计划校验的操作，因 I/O 失败留下了需要手工修复的工程。

建议：所有相关文件先生成临时稿并检查读取版本，再提交；失败时恢复已替换文件，或留下明确可执行的恢复记录。文档应区分“计划通过才开始写入”和“写入失败也能保持工程一致”。

验收：逐个模拟事件表、清单、布局的写入失败，工程保持原状态，重试相同计划成功。

### R04：倒计时评估检查了词形，没有检查结束条件的含义

位置：[grade.py](../../skills/construct3-agent-plugin/evals/grade.py)，第 74–171 行，特别是第 126–130 行。

评估只要求重载布局的事件条件中出现倒计时变量名，没有检查比较运算符或阈值。

反例保留原事件，增加从 30 开始、每帧减 `dt`、启动时复位和显示时间的倒计时，却在 `Countdown > 0` 时重载布局。这个实现把结束条件写反：初始值就满足重载条件。实际 grader 的全部断言仍通过，项目 checker 也通过且没有警告。

影响：错误实现可以成为高分样本，后续对提示词、工具或技能版本的优劣判断失去依据。这个反例验证的是 grader 误判，没有在编辑器中试玩。

建议：增加正反条件的对抗样本，并对关键行为运行输入和状态验收：到期前不重载、到期后重载、下一轮恢复完整时间。静态断言可以保留，用于定位失败原因。

### R05：trace 对技能加载的统计同时存在误报和漏报

位置：[trace.py](../../skills/construct3-agent-plugin/evals/trace.py)，第 35–72 行。

`read_skill_md` 要求工具名为 `Read` 或 `Skill`，且调用内容包含 `SKILL.md`。正常 `Skill` 调用的参数只有技能名，因此不会命中；读取任何其他技能的 `SKILL.md` 却会命中。

最小输入结果：`Skill: construct3-agent-plugin` 得到 `false`；`Read: /skills/unrelated/SKILL.md` 得到 `true`。这直接影响“模型是否读了本技能”的证据。

建议：按工具种类分别检查目标技能名或文件路径，再结合工具结果确认读取成功；与 trigger runner 共用这项判定。

验收：目标技能调用、目标文件成功读取、其他技能读取、目标文件读取失败都有独立正确结果。

### R06：触发评估没有区分“未触发”与“没有完成”

位置：[run_trigger_eval.py](../../skills/construct3-agent-plugin/evals/run_trigger_eval.py)，第 43–93、119–135 行。

发现加载工具调用时立即返回 `true`，不等工具返回；客户端曾输出一条 assistant 消息后被定时器杀掉，则返回 `false`，不要求最终结果或成功退出。

两个模拟客户端分别证明：读取不存在的目标 `SKILL.md` 被计为触发；输出 assistant 消息后超时、没有 result 的运行被计为未触发。后者会让负样本通过，前者会让正样本通过。

建议：返回“成功加载、正常未触发、到达工具预算、超时、客户端失败、加载失败”等明确状态。超时和失败样本不要进入正常触发率分母；是否把工具预算作为评估截断，需要单独记录。stderr 应保存供诊断。

验收：两种探针都不能得到正常通过结果，报告能说明失败类别与有效样本数。

### R07：技能入口超过项目自己的 token 预算，自动检查没有覆盖它

位置：[skills/AGENTS.md](../../skills/AGENTS.md)，第 29–34 行；[test_skill_spec.py](../../tests/test_skill_spec.py)，第 36–37 行；[SKILL.md](../../skills/construct3-agent-plugin/SKILL.md)。

仓库要求入口低于 5000 token，并要求每次激活读完。用本机 `tiktoken` 的 `o200k_base` 与 `cl100k_base` 测量，两个结果均超过这个预算。测试仅检查行数小于 500，所以全文仍可通过检查。不同模型的 tokenizer 不同，这里没有推算 Claude 的精确 token 数。

入口的长脚本表、完整编辑计划说明、Git 工作规则和完整交付流程均在激活时加载。具体修改一个参数的任务，也需要承担生成完整游戏和外观审查说明的阅读成本。

建议：先加“任务、读取内容、完成证据”的短分流表，再把计划语法、生成项目和完整验收细节放到已有 references。用固定 tokenizer 检查预算，并用小任务评估确认分流没有让模型漏掉必要步骤。

验收：既满足入口预算，又能在不点名技能的查询、局部修复和完整项目任务中找到正确路径。不能只用删行数证明效果。

### R08：安装器发现已有 AGENTS.md 配置后，遗漏其他客户端入口的检查

位置：[install.py](../../skills/construct3-agent-plugin/scripts/install.py)，第 83–119 行。

`add_block()` 发现任一指令文件已有仓库和技能配置，就立即返回。补充 `CLAUDE.md` 中 `@AGENTS.md` 的逻辑在这个返回之后。

探针使用已配置的 `AGENTS.md` 和一个只有项目说明的 `CLAUDE.md`。函数输出“already names the clone and this skill”，但 `CLAUDE.md` 仍无入口引用。文件是否齐全与不同客户端是否实际能发现它，是两件事；本次没有用真实 Claude Code 验证后果。

这是安装完整性和诊断不足，不应靠覆盖用户的指令文件解决。建议独立检查引用；缺失时给出精确提示，或在允许的安装策略下仅追加引用。`--no-block` 仍应尊重用户选择。

## 待验证的风险与设计不足

### R09：固定 `agents` 分支把不同会话的工作合在一起

位置：[SKILL.md](../../skills/construct3-agent-plugin/SKILL.md)，第 44–51 行。

指令要求在当前工程初始化 Git，并统一切换到 `agents`，没有先检查工作区、当前分支、分支占用或另一个会话。并行任务可能在同一分支混入修改；分支已被其他 worktree 使用时，切换也会被 Git 拒绝。

建议：遵从工程自身的 Git 规则，检查状态，使用每个任务独立的分支和 worktree。不要让一个通用 Construct 技能决定用户工程最终由谁合并。并发模型任务与实际冲突场景尚未运行。

### R10：打开工程会自动安装其携带的 addon

位置：[open_in_editor.py](../../skills/construct3-agent-plugin/scripts/open_in_editor.py)，第 176–193 行。

`RESULT_JS` 发现 `addonConfirmInstallDialog` 就点击安装，只在结果中记录 warning。“检查能否打开一个下载的工程”因此包含了安装工程携带的代码，调用方没有单独的拒绝或允许选项。

这项行为可从源码确认；没有安装恶意 addon，也没有证明浏览器隔离被突破。风险在于来自外部工程的代码被默认接受，且安装结果保存在后续复用的浏览器 profile 中。

建议：默认报告所需 addon 的身份并停止；显式启用安装，或按已确认的白名单接受。外部工程使用隔离 profile，安装日志保留版本和内容指纹。

### R11：技能刷新没有保留本地修改的恢复路径

位置：[install.py](../../skills/construct3-agent-plugin/scripts/install.py)，第 58–68 行；[SKILL.md](../../skills/construct3-agent-plugin/SKILL.md)，第 42–43 行。

镜像探针中，修改过的 `SKILL.md` 被源版本覆盖，额外的 `private-helper.py` 被删除，没有留下备份。源目录作为唯一权威是仓库明确的设计，因此这些文件并非安装器承诺支持的扩展；问题是发现漂移就要求刷新，而刷新过程没有提供恢复能力。

生成器 helper 的刷新已经会识别用户修改，技能文件刷新却没有相同保护。

建议：安装时记录源文件指纹，区分源升级与本地修改；检测到本地修改时保存可恢复副本并报告位置。先完整准备新版，再替换整份技能，避免中途失败产生新旧混合的副本。

### R12：修复一处机制，被指令扩大成全项目治理

位置：[SKILL.md](../../skills/construct3-agent-plugin/SKILL.md)，第 249–297 行；[review_design.py](../../skills/construct3-agent-plugin/scripts/review_design.py)，第 918–952 行。

流程要求修复 checker 的每一行、处理所有 design findings、回答所有问题，再审查全部外观直到每个答案为否。`review_design.py` 默认遍历所有事件表，虽然它有 `--sheets`，入口流程没有按修改范围使用。

对用户已有项目的一处 bug，这会把风格建议、旧代码和无关画面一起推入修改范围。启发式 findings 也不全是错误：同一技能的验证参考已经记录了官方项目中存在有意保留的命中。

建议：阻止加载和修改引入的问题必须修；修改影响的逻辑必须试玩；未触及的旧警告和风格建议留在审查结果。完整 design/look 治理由完整项目任务触发。局部任务是否实际被扩大、消耗多少 token，尚未跑模型评估。

### R13：触发评估的并行样本共用可写工作区

位置：[run_trigger_eval.py](../../skills/construct3-agent-plugin/evals/run_trigger_eval.py)，第 53–61、119–132 行。

所有查询和重复运行都以同一 `project` 为 cwd，并通过 `ThreadPoolExecutor` 并行。命令没有配置只读工具范围，也没有每样本复制、文件哈希校验或重置。正负样本中包含修复、改名、生成工程等会引导写文件的请求。

即使在检测到触发后立即停止，触发之前的工具调用也可能修改项目或指令文件。不同样本因而可能看到不同输入，用户配置的客户端权限也会改变评估行为。

建议：每个样本用独立临时项目和客户端设置；以只读工具测触发，记录实际参数、模型标识和项目指纹。没有运行真实并行客户端，因此污染发生率未知。

### R14：更新工作流把第一个检查的结果当成全部检查

位置：[update.yml](../../.github/workflows/update.yml)，第 98–119 行。

`gh pr checks` 的结果仅取 `.[0].state`；第一个 PASS 就输出“All checks passed”。等待循环耗尽后没有失败退出，仍会调用自动合并。工作流自身也没有执行根目录要求的 pytest 和 compileall，仓库没有另外提交测试工作流。

因此，本文件不能保证数据与 plugin 的改动经过全部验证。GitHub 分支保护可能提供额外门禁，但本次没有读取线上规则，不能据此断言失败的 PR 已经被合并。

建议：在更新任务中实际运行所需检查；检查集合应全部成功，pending、空集合和超时应有明确失败策略；同时核对线上 required checks。

### R15：导出打包强制改成 Use worker Auto

位置：[export_project.py](../../skills/construct3-agent-plugin/scripts/export_project.py)，第 542–555 行。

打包阶段不论工程设置为 `dom`、`worker` 还是 `auto`，都把副本改为 `auto`，原工程则保持原设置。这个行为写在脚本说明里，属于现有策略，不能当作无意拼写错误。

不足在于预览所验证的配置与实际导出的配置可能不同。是否真的改变 runtime、影响依赖主线程环境的脚本，取决于工程和 addon，本次没有做运行验证。

建议：默认保留配置；如确有导出要求，说明触发条件并提供显式覆盖选项。验收要同时检查预览和最终导出的实际 runtime。

### R16：解包在过滤文件之前读取所有成员

位置：[pack_project.py](../../skills/construct3-agent-plugin/scripts/pack_project.py)，第 95–111 行。

`from_archive()` 对整个 ZIP 的每个文件执行 `z.read()` 并保存在字典里；之后才筛出编辑器文件。没有成员数量、单文件解压大小、总解压大小或压缩比上限。最终被排除的巨大文件也会占用内存。

这是可确认的资源保护缺口；没有制造资源耗尽或测量崩溃阈值。建议先检查中央目录和路径，只读取需要的文件，并提供有边界的可配置上限与流式复制。

## 修复顺序与验收条件

1. 先处理 R01、R02 和 R10：限制删除目标、保留旧导出、把外部 addon 安装变成显式动作。它们涉及文件损失与代码接受边界。
